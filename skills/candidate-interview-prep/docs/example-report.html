Topics and questions

1. Performance, databases and scaling

Diagnostic method under pressure, and depth with real systems.
Core1a. A store you run grows 20x in traffic over a quarter. Walk me through what breaks first, in what order, and how you'd find out before customers do.
Now it's a flash sale instead: 50x for two hours, mostly logged-in shoppers with carts. What changes?

Listen for: separating cacheable from uncacheable traffic; PHP workers queueing; database connections and lock contention; cache stampedes; load testing with a realistic mix; alerting on saturation, not just errors.

Red flag: "add more servers" with no idea which resource runs out first.

Other ways to ask:
  • What usually fails first when a PHP app gets much busier, and why?
  • Your traffic doubles every month. What would you measure this week?
Acceptable answer: names page caching, the database and server resources as likely limits, and suggests monitoring and adding capacity.
Strong answer: estimates capacity (e.g. 40 PHP workers × 250 ms = 160 uncached req/s), expects logged-in cart traffic to bypass the page cache and hit workers and the DB, checks slow queries and lock waits, protects hot cache keys from stampedes, moves emails and webhooks to a queue, and load-tests with k6 or JMeter using a realistic logged-in mix before the sale.
If they're stuck: ask what happens to a single request when every PHP worker is busy.
Core1b. You took checkout p95 from 2.8 s to 900 ms. Starting fresh: a page that took 300 ms now takes 4 s after a deploy, but only for some users. How do you find the layer responsible before changing anything?

Listen for: reproducing and segmenting (which users, which pages); TTFB vs. front-end time; APM traces or Query Monitor; comparing before and after the deploy; changing one thing at a time.

Other ways to ask:
  • How do you debug a slowdown you can't reproduce locally?
  • Tell me about the checkout work: how did you know where the time was going?
Acceptable answer: checks logs and the slow query log, profiles the request, and looks at what the deploy changed.
Strong answer: notices "only some users" points at uncached or personalised paths, compares a trace from an affected user with one from an unaffected user, finds e.g. a new meta_query without an index, confirms with EXPLAIN, fixes it, and verifies with before/after p95.
If time1c. When does caching make a problem worse instead of better?

Listen for: stale or leaked personal data, stampedes on expiry, hiding a slow query until the cache is cold, invalidation complexity.

Other ways to ask:
  • Tell me about a caching bug you've seen.
  • How do you decide what not to cache?
Acceptable answer: mentions stale data and invalidation being hard.
Strong answer: gives a concrete case (a cached page leaking a logged-in user's name through a cached Set-Cookie), and how they'd prevent it: cache keys, vary headers, bypass rules, locking or early recomputation for hot keys.

2. Testing and quality

Whether tests are part of the work, and how they decide what's worth testing.
Core2a. You inherit a plugin with no tests that breaks every release. What do you test first, and how do you get the team to keep it up?

Listen for: starting from what actually breaks; characterization tests around risky code; CI that blocks merges; keeping tests fast.

Other ways to ask:
  • How do you decide what's worth testing?
  • Tell me about a bug that tests should have caught. Why didn't they?
Acceptable answer: adds unit tests for core functions and runs them in CI.
Strong answer: pulls the last few incidents, writes integration tests around those paths first, adds a regression test with every bug fix, runs PHPUnit and static analysis in CI on every PR, and tracks flaky tests rather than retrying them.
If time2b. How would you catch a performance regression before it ships?

Listen for: query-count or timing budgets in CI, load tests on staging, comparing against a baseline.

Other ways to ask:
  • Can tests protect performance, or only correctness?
  • A PR adds 40 queries to a page. How would anyone notice?
Acceptable answer: review carefully and monitor after release.
Strong answer: asserts query counts for key pages in integration tests, runs a short load test against staging on merge, and alerts when p95 moves beyond a threshold.
